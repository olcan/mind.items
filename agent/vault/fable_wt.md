#agent/vault/fable_wt is the _writable_ `fable_wt` persona of the [vault chat agent](#agent/vault): Claude Fable 5.1 at maximum effort, with the worker's file and edit tools and a shell that waits for each command by default (run `test.sh` and `lint.sh` before proposing; no network), running inside the chat item's own git worktree `worktrees/chat_<item>` on the vault host (registry `agents/bridge.toml`, `writable = true`, cost limit $10; design `notes/design/mind_bridge_writable.md`). The worktree is created for the chat's first request and reused by every later one; only that worktree is writable (the main repository is read-only, other worktrees and the vault's harness state are hidden), each run's git-trackable changes (ignored files are not staged) are committed as the worktree's proposal, and nothing reaches `main` until the owner MERGES the worktree (`merge_worktrees.sh` lands the proposal); retiring it instead (`remove_worktrees.sh`) discards the proposal. Either way the chat's next request starts a fresh `worktrees/chat_<item>_<n>`. Tag a chat item `#agent/vault/fable_wt` (visible or hidden) and end it with a `\<<user>>` message, or use the `/fable_wt` [chat command](#chat/fable_wt); replies arrive as `\<<agent('vault/fable_wt · run …')>>`. A request already claimed by a run is not run again (the run's receipt on the vault host records the claim; it, the worktree's run files and any accepted/rejected decision tag are the evidence to investigate what happened; edit the message to run it again). A reply of `finalization-failed` means the run's worktree could not be committed and awaits the owner. This item exists so the persona tag has one uniquely labelled item to depend on.
